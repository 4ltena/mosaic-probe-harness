# 設計メモ

画像を渡すと「モザイクが必要な部位が、写っていない、または十分に処理されている確率 `p_ok`」を数値 1 個で返す。判定のしきい値は持たない。

## 構成

```
呼び出し側 ──(REST / MCP)──> ハーネス(Node, TypeScript) ──(HTTP)──> llama-server(llama.cpp)
                             形式判定・レイヤー描画・確率の計算          VLM（画像入力、logprobs）
```

- ハーネスだけを LAN に出す。`llama-server` は `127.0.0.1`（複数台のときは専用リンクの IP）に限る。
- 画像は保存しない。ログに画像・base64・キーを出さない。

## 確率の作り方

1. モデルに「A=対象なし / B=処理済み / C=未処理・不十分」の **1 文字だけ**を答えさせる（`max_tokens: 1`、思考オフ）。
2. 1 トークン目の `logprobs`（上位 20）から A/B/C の確率を取り、合計を 1 に正規化する。ラベルの質量が 0.5 未満なら 1 回だけ再試行し、だめなら失敗にする（値を作らない）。
3. `q = C/(B+C)` に Platt 較正（`calibration.json`）を当て、`p_ok = 1 − (1 − none) × cal(q)` を返す。較正が無ければ恒等。
4. モデルの自己申告の確率は使わない。質が低く、較正できないため。

## Pi の使い方

- 土台は `@earendil-works/pi-ai` と `pi-agent-core`（MIT）。**Pi 本体は改造せず、依存として使う。**
- pi-ai の `llama-cpp-classify` は画像入力に対応しないので、Pi の classifier 抽象（`createProvider` の `classifiers`、`models.classify`、`labelProbabilities`）に載せた**画像対応の自作 classifier**（`/v1/chat/completions` ＋ `logprobs`）を使う。
- `pi-agent-core` の `Agent` は再判定（`RECHECK=1`、既定オフ）だけに使う。境界付近の画像を領域ごとに切り出して判定し、**`p_ok` を下げることしかしない**。
- **モデルに渡すツールは自作の `crop` だけ。** Pi の標準ツール（read / bash / edit / write など）は導入もしない。`tests/tool-scope.test.ts` で固定している。

## レイヤー安全

モザイクが別レイヤーだと、非表示や削除で解除できる。PSD は「見えているとおり」「非表示も表示」「モザイク名のレイヤーを非表示」「可視レイヤーを 1 枚ずつ外す」を判定し、**最小の `p_ok`** を返す。1 件でも失敗したら全体を失敗にする。限界は README の「PSD 合成の制限事項」。

## 複数台

各台で独立した `llama-server` を動かし、ハーネスが振り分ける（複製）。1 台でも同じ設定・同じ挙動で動く。失敗した台は 15 秒外し、別の台で 1 回だけ再試行する（1 台のときは外さない）。

**RPC による 1 モデルの分割は採らない。** llama.cpp の RPC はパイプライン方式で 1 リクエストは速くならず、メモリを足せるだけ。画像入力との併用も未検証。メモリが足りる（1 台 512 GB）ので不要。

## 失敗の扱い

どの経路でも、失敗のときに数値を返さない。呼び出し側がエラーを `0` や `1` で埋めて続行することを防ぐため。MCP は `isError: true`（HTTP は 200）、REST は `{"error": …}` とステータスで返す。

## 非目標

OK/NG の判定、バッチ処理、画像の保存、判定理由の返却、TLS の終端（リバースプロキシは接続元 IP の判定を崩すので置かない）。
